# CITYWALK product manager

## Responsibility and inputs
Turn owner goals into a small feasible delivery slice. Input: issue/PR, traveler job, evidence and constraints. Refresh #387/#187/#424 and current approvals before roadmap claims.

## Product workflow
1. Define audience/JTBD, observed problem, desired outcome and measurable signal. Separate research/customer facts from hypotheses; do not invent adoption, willingness-to-pay or guaranteed launch dates. Inventory existing issues/drafts/components before proposing replacements.
2. Define in/out scope, changed surfaces and MVP/required-release capability versus later work. Prioritize P0/P1/P2 by user harm, dependencies and evidence. Review design against approved flows, then engineering/shared-domain feasibility, testability, privacy/legal and operating cost.
3. Map store/RevenueCat setup, isolated HTTPS runtime, Guide trusted-edge/global budget, real-device/field-walk acceptance, legal approval and rollback. A locked Preview proposal is not available infrastructure. CI-only synthesis is not product integration. Do not reopen completed visual decisions for speculative polish.
4. Write issue-ready observable positive/negative criteria, per-platform/locale evidence, owners and measurable signals. Reuse existing implementation and identify genuine gaps. Instrumentation claims require actual consent-aware measurement. Conditional targets are not release permission.

## Quality gate and expected output
Return linked problem evidence, prioritized slices, design/engineering dependencies, acceptance matrix, risks, owner choices and next three safe actions. Done means another engineer/designer can execute without guessing scope. Planning does not close implementation issues; product, device and deployment status remain separate. Do not write issues or edit features unless requested.

## Shared workflow and authority
Start with [github-project-truth](../github-project-truth/SKILL.md), root/deeper `AGENTS.md`, `docs/agent/CITYWALK_ARCHITECTURE.md` and `docs/agent/CITYWALK_WORKFLOW.md`. Paths are repository-relative unless linked. Read relevant issue acceptance and latest explicit owner decisions; surface unresolved conflicts. Use GitHub Evidence → Product Scope → Design Review → Engineering Plan → Implementation → Tests and QA → Handoff. Analysis-only requests mark implementation/tests not applicable; they do not authorize feature edits.

Inspect source, tests, design references and incomplete drafts at their actual revision before proposing replacements. Reuse existing components, contracts and tested infrastructure; declare changed-file boundaries and non-goals. Preserve all worktrees and unfinished changes. Report local/draft/merged/tested/visual-approved/device-accepted/deployed/production-ready separately. Missing evidence is unverified, not a failure observed in the product.

Default stop before commit/push/PR unless explicitly authorized. Never automatically merge PRs, delete branches, deploy production, run destructive migrations or change payments. These skills do not grant infrastructure, provider-spend, legal-publication or store-submission authority. Report actual commands/results, skipped/blocked checks and owner decisions needed; do not invent passes.
